## 1. 结论

1. LVGL 9.1.0 包含 DIRECT 双全屏缓冲的增量同步优化，但这不是所有“双全屏缓冲慢”问题的通用修复，也不是 v9 独有。上游 v8.3.10、v8.4.0 已有对应实现。
2. SPI 屏双全屏缓冲比双半屏慢的旧问题 #2038，已在 v8 通过显式 `full_refresh` 开关处理。工程的 8.2.0 已具有该机制，不需要为此升级到 v9。
3. 当前工作区实际启用的是“单块全屏容量缓冲 + 局部刷新”，不是双全屏缓冲。历史双缓冲实验的开关、驱动、测量结果不在当前配置内，不能直接断言其根因。
4. 当前 `flush_cb` 同步等待 SPI DMA 结束，无法利用双缓冲实现绘制与传输重叠。这是源码可以确认的性能限制；它是否是具体页面的最大瓶颈，需要测量。
5. 建议先在 8.2.0 实现异步 DMA 刷新，比较双条带、双半屏、双全屏容量的局部刷新。若确实需要完整常驻帧图，再评估回移植 DIRECT 同步算法。仅为双缓冲性能整体升级至 9.1.0，收益尚无证据、改动成本较高。
6. v9.1.0 并未包含所有后续相关修复：DIRECT 双缓冲多余等待的 PR #6120 于 2024-05-17 合入，晚于 v9.1.0 的 2024-03-20 发布日期。本地 9.1.0 仍有该等待。
7. 本地 v8.3.10 有另一项重要区别：即使 `full_refresh=direct_mode=0`，两块恰好全屏容量的缓冲仍会走 `full_sized` 的绘制前等待，限制 SPI 绘制/传输重叠。不能把“已有 DIRECT 优化”等同于“双全屏 PARTIAL 更快”。8.2.0 与 9.1.0 的相应等待位置不同。
8. 离线测试确认本地 v8.3.10 和 v9.1.0 的 `_lv_area_diff()` 都存在单行差集漏覆盖；启用或回移植 DIRECT 前需修复并验证。详情与复现命令见综合方案。

## 3. 网上所说的修复，至少要区分三件事

### 3.1 SPI 双全屏缓冲自动进入特殊模式：v8 已解决

[Issue #2038](https://github.com/lvgl/lvgl/issues/2038) 的原始描述正是 SPI 屏使用两块全屏缓冲时，benchmark 比两块半屏缓冲慢。旧代码按缓冲容量识别 `true_double_buf`，提问者禁用该识别后性能改善。

[维护者回复](https://github.com/lvgl/lvgl/issues/2038#issuecomment-819561545) 说明 v8 增加 `full_refresh`，默认关闭。工程 8.2.0 确实按显式 `full_refresh/direct_mode` 决定刷新行为，未找到旧的 `lv_disp_is_true_double_buf` 自动识别路径。

因此，两块缓冲都分配到全屏大小时，仍可以保持 `full_refresh=0, direct_mode=0`。不要因模板中“Double buffering”的例子就默认开启全屏重绘；该例子强调的是能切换帧缓冲地址的显示控制器场景。

补充限定：这里描述的是模式选择，不保证每个 v8 版本的等待时序相同。v8.3.10 `src/core/lv_refr.c:708` 和 `:1282` 仍按容量选择等待位置，普通局部刷新也受影响；工程 8.2.0 没有这两个 `full_sized` 分支。

### 3.2 DIRECT 双缓冲减少冗余同步：v9.1.0 有，v8.3 也有

[Issue #4262](https://github.com/lvgl/lvgl/issues/4262) 指出：每轮把所有刚更新区域复制到另一缓冲，下一轮又重绘相同区域，会浪费内存带宽。全屏动画尤其明显。

对应上游记录：

| 记录 | 合入日期 | 内容 |
|---|---|---|
| [PR #4497](https://github.com/lvgl/lvgl/pull/4497) | 2023-08-29 | `release/v8.3` 的高效 DIRECT 同步算法，提交 `336f24127ab9032cd7b2ac67f25f785cf3b64033` |
| [PR #4526](https://github.com/lvgl/lvgl/pull/4526) | 2023-09-07 | 修复单缓冲 DIRECT 仍记录同步区域造成的泄漏，提交 `9787d47d0b6a000e662a65c8a9dc456e47e9e331` |
| [PR #4443](https://github.com/lvgl/lvgl/pull/4443) | 2023-10-10 | 主线实现高效 DIRECT 同步，提交 `8c63327f668ba341894281971de3386885b8de35` |

通过 GitHub contents API 检查标签源码：v8.3.9 无 `refr_sync_areas`；v8.3.10、v8.4.0 有该函数且记录区域受 `direct_mode && buf2` 条件保护；v9.0.0 已有同步算法。因此它并不是 9.1.0 才首次提供的特性。

本地 9.1.0 的 `src/core/lv_refr.c:372` 顺序为：合并本轮脏区域、`refr_sync_areas()`、渲染本轮区域。`:460` 的同步算法从上轮待同步区域中扣除本轮即将重绘的部分，再从较新的缓冲复制剩余区域到待绘制缓冲。

可用集合表达其意图：`需要同步的区域 = 上轮更新区域 - 本轮重绘区域`。

- 同一个区域连续动画：大部分同步可以省掉。
- 连续全屏重绘：同步区域可为空。
- 两轮更新区域互不重叠：仍需要同步上轮更新内容。

这是减少内存复制，不是减少 SPI 必须传出的像素。也不能拿“缺少同步导致画面错误”的旧 DIRECT 配置作为正确的性能基线。

### 3.3 DIRECT 多余等待：v9.1.0 尚未解决

[PR #6120](https://github.com/lvgl/lvgl/pull/6120) 删除刷新结束、仅记录待同步区域之前的一次 `wait_for_flushing()`。本地 9.1.0 `src/core/lv_refr.c:386` 仍存在此调用。

该修复没有删除同步前必须保留的等待，也不意味着 DIRECT 在 SPI 屏上变成了完全重叠的绘制/发送流水线。不能通过随意删掉所有等待来“优化”。

[相关讨论 #6118 的维护者回复](https://github.com/lvgl/lvgl/issues/6118#issuecomment-2076687023) 明确建议：对于具有显示控制器的 SPI/并口屏幕，PARTIAL 模式通常更合适。

## 4. 9.1.0 在本硬件上是否更快

没有上板对照数据，不能给出 FPS 或百分比承诺。源码支持以下判断：

| 使用方式 | 9.1.0 相对工程 8.2.0 的预期 |
|---|---|
| 继续使用同步 `LCD_DisplayArea()`，只增加第二缓冲 | 绘制与 SPI 传输仍串行，不能指望靠版本升级获得双缓冲并行收益 |
| 两块全屏容量，PARTIAL / v8 普通局部刷新 | 8.2 已支持；收益取决于异步驱动、分块大小、脏区域与绘制时间 |
| FULL / `full_refresh=1` | 两个版本都整屏重绘；一个小控件变化也会导致大量额外工作 |
| DIRECT 双全屏，旧实现每轮全量同步 | 高效同步可减少重复拷贝，尤其是重叠动画；v8.3 补丁同样能提供此能力 |
| 当前工程直接切 `direct_mode=1` | 8.2 没有自动区域同步，而且现有 SPI flush 语义不匹配，必须先保证正确性 |

STM32F407 没有 LTDC、DMA2D、NEON、Helium，也没有需要维护的 M7 式数据缓存。9.1.0 的多绘制单元、NEON/Helium 路径不能自动变成本机加速来源。外部 SRAM 的 CPU 绘制与 DMA 读取还可能争用总线，实际重叠收益必须测量。

SPI1 当前为 8-bit，APB2=HCLK/2，SPI 分频=2，所以在 192/216/240 MHz 三档下，SPI 理论时钟分别为 48/54/60 MHz。仅计算 320*240*2 字节线速传输：

| CPU | SPI | 一整屏理论传输时间 |
|---:|---:|---:|
| 192 MHz | 48 MHz | 25.60 ms |
| 216 MHz | 54 MHz | 22.76 ms |
| 240 MHz | 60 MHz | 20.48 ms |

这些是不含绘制、总线等待、窗口命令及分段间隙的下限，不是实测。当前刷新定时器还是 30 ms，不应把 1 ms/6 ms 的 handler 轮询误认为每秒 1000/167 次显示更新。旧文档中的 84 MHz SPI 描述也不适用于当前时钟配置。

同步路径时间近似 `绘制时间 + 发送时间`；充分分块、异步传输时，稳态理想值才可能接近 `max(绘制时间, 发送时间)`，还要加流水线首尾及切块开销。

双全屏容量不一定比双半屏快：整屏失效时，一个大块绘制完成前无法开始发送该块；半屏/条带能较早开始 DMA，让后续块与传输重叠。更小的块又会增加窗口设置、渲染遍历和回调次数，所以应测量选型。

## 5. 回移植到 8.2.0 的可行性与范围

### 5.1 推荐优先项：异步局部刷新

无需回移植 v9 的渲染内核。保留 `full_refresh=0, direct_mode=0`，改进本机显示移植层：

- `flush_cb` 设置窗口、提交 DMA 后返回；全部分段完成后才通知 `lv_disp_flush_ready()`。
- SPI1 目前是 8-bit DMA，全屏 153600 B 超过单次 HAL 长度上限，需要异步续传状态机；不能只启动第一段就宣告完成。
- 接入现有 `HAL_SPI_TxCpltCallback`/error callback，区分显示所有者；保留 NES/视频已有回调行为。等待用 CMSIS-RTOS V2 静态信号量等现有机制，明确超时和错误退出。
- 异步化后，`lv_timer_handler()` 返回不再保证 DMA 空闲。在 `lvgl_ui_pause_point()` 确认移交 LCD/SPI1 之前，必须排空本轮所有 DMA 分段并释放片选；不能仅等待单段 HAL READY。
- 双缓冲均使用 DMA 可访问内存；初次试验用 SRAMEX。不要把 DMA 缓冲放 CCM，也不要未经内存规划把 LVGL 常驻缓冲塞入视频专用 80 KB 池。

初步比较每块 24/48/120/240 行。两块 RGB565 缓冲分别合计 30/60/150/300 KiB。系统资源表中的原有 150 KiB 缓冲是否仍被其他调用者引用，要单独审计；若另行分配条带却保留原缓冲，上述容量不代表系统实际节省量。

### 5.2 如果必须使用 DIRECT 双全屏：可回移植，改动中等

优先以 v8.3.10/v8.4.0 及 #4497 + #4526 为参照，再结合 v9.1.0 的等待语义。不要整文件替换 `lv_refr.c`。

| 范围 | 工程缺失内容 / 所需处理 |
|---|---|
| `src/core/lv_refr.c` | 同步列表更新、渲染前差集同步、正确的缓冲切换和等待位置 |
| `src/hal/lv_hal_disp.h/.c` | `sync_areas` 字段、初始化与释放；切换缓冲/分辨率时处理旧状态 |
| `src/misc/lv_area.h/.c` | 当前没有 `_lv_area_diff`，需补矩形差集运算及边界验证 |
| `src/draw/lv_draw.h` 及软件后端，或局部复制辅助函数 | 当前 `lv_draw_ctx_t` 没有 v8.3 补丁调用的 `buffer_copy`；可补接口，或对本机固定 RGB565 用带 stride 的逐行复制 |
| 显示移植层 | 处理完整帧缓冲基址、脏区偏移、stride、每轮提交次数及 RGB565 字节序 |

显示移植尤其容易漏改：

- 工程 8.2.0 的 DIRECT 路径把 `draw_ctx->buf_area` 设为整屏，`draw_buf_flush()` 又把这个区域交给驱动。存在多个脏区时，当前驱动可能在每个脏区后都传整屏。若用 DIRECT，应明确只在本轮最后一次 flush 发整屏，或配套实现正确的脏区发送契约。
- v9.1.0 DIRECT 向 flush 提供实际刷新区域和全帧基址。不能把基址当作脏矩形的紧密数组直接交给 `LCD_DisplayArea()`；需要偏移及逐行 stride 处理，或收集区域后统一发送。
- 对本项目 SPI 来说，维持两个完整图像再同步它们的成本，可能高于 PARTIAL 直接更新 ST7789 GRAM 的成本。回移植“可行”不等于本机“值得默认启用”。

原始补丁的链表插入后直接解引用，不能忽视本机 SRAMEX 分配失败。移植时应增加容量/失败处理，失败时保证下次完整重绘或安全退化，不得丢掉仍需同步的数据。矩形差集还应覆盖单行、单列、相切、包含、重复重叠等边界；不能仅以页面无明显花屏为验收。

### 5.3 整体升级 v9.1.0：范围明显更大

除 Keil 源文件清单和 `lv_conf.h` 外，至少要迁移显示/输入驱动、内存适配、图片描述符与资源、XBF 字体代理及 GUI API。

本地 `docs/CHANGELOG.rst` 明确列出：

- `lv_disp_drv_t`、`lv_disp_draw_buf_t` 被移除，换成新 display API；缓冲大小单位由像素变成字节。
- `lv_color_t` 固定为 RGB888，即使显示使用 RGB565。工程 `GUI/GUI_Image.c:715` 按 `sizeof(lv_color_t)` 分配图片，`:751` 用该类型写像素，不能只改函数名。
- `LV_COLOR_16_SWAP` 被移除，RGB565 传输字节序需要显式处理。DIRECT 持久帧缓冲若原地 swap 后继续参与绘制/同步，必须恢复其原生格式或采用独立转换策略。
- 字体回调、图片格式、底层绘制架构等也需适配；v8 兼容宏不能解决全部语义变化。

若未来因其他 v9 功能决定迁移，应重新选择含所需修复的明确版本，并做 Flash/SRAM/栈和实际页面回归；不能单凭“9.1.0 版本更高”推导性能更优。

## 6. 上板验证方案

第一轮只比较 8.2.0 下的基线与异步双缓冲，先回答驱动/分块能带来多少收益。第二轮才在相同显示策略、时钟与页面下比较 v8 回移植和 v9，避免混淆版本与驱动收益。

测试场景：主菜单焦点切换、文件列表连续滚动、Toast 动画、页面全屏切换，以及暂停/恢复 GUI 后的第一次刷新。

记录：渲染 CPU 时间、DMA 开始至最终完成时间、等待时间、每轮 flush 数、SPI 总字节数、同步复制字节数、显示完成间隔的平均/P95/最大值、CPU 占用、SRAMEX 峰值/碎片及 LVGL 栈余量。

使用 DWT 周期计数或 GPIO/逻辑分析仪区分渲染和传输。异步化后 `monitor_cb` 耗时可能不含最后一段 DMA，不能只看 LVGL FPS 就宣称最终显示性能改善。比较时固定 30 ms 刷新周期；需要测峰值时另开统一更短周期的一组实验。

DIRECT 回移植的额外验证：矩形差集的主机端边界测试；交替更新不相交区域、多区域重叠、整屏切换和分配失败；两缓冲与单缓冲参考图逐像素比较。完成实际代码修改后再运行 Keil 编译检查和上板回归。

推荐实施顺序：8.2.0 异步 PARTIAL 双缓冲 → 实测选择条带/半屏/全屏容量 → 有完整常驻帧图需求时回移植 DIRECT → 因独立功能需求再决定是否整体升级 v9。
