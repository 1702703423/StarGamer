# LVGL 8.3.10 调研与 Star Gamer 综合优化方案

日期：2026-09-23。工程基线：`52af783`，LVGL 8.2.0。

对照目录：`C:/Users/ZLK/Documents/Cubemx/lvgl-8.3.10/lvgl-8.3.10` 与 `C:/Users/ZLK/Documents/Cubemx/lvgl-9.1.0/lvgl-9.1.0`。下文第三方文件行号相对各自源码根目录，工程文件行号相对工程根目录。

本次完成源码对比、Keil XML 源文件清单检查、上游记录核实和几何算法离线验证。没有修改固件，没有进行固件构建或硬件性能测量。前一轮依据见 [9.1.0 调研报告](LVGL-9.1.0-Buffer-Research.md)。

## 1. 最终建议

近期推荐配置：**保留 8.2.0，普通局部刷新，SRAMEX 双 48 行缓冲，异步 SPI DMA，减少不必要的整屏失效。** 48 行是便于验证的起点，不是已经测出的最优值。

后续版本升级优先评估 **8.3.10，而非为了双缓冲直接迁移到 9.1.0**。但升级应作为独立实验：8.3.10 有 DIRECT 同步能力和其他修复，也有全屏容量等待分支；它不保证所有模式都比 8.2.0 快。

不建议当前项目默认启用 DIRECT 双全屏：它需要两个完整图像及同步复制，而 SPI ST7789 自带 GRAM，普通局部刷新不需要复制未变化像素。此外，本次已确认两份后续版本的 DIRECT 差集算法存在边界问题。

实施顺序：建立测量基线 → 缩小无效重绘 → 异步双条带 → 扫描缓冲大小 → 对照升级 8.3.10 → 按测量结果优化字形读取和绘制成本。DIRECT 保留为有明确需求时的可选路线。

### 2.2 新发现：全屏容量影响等待位置

v8.3.10 `refr_area_part()` 在绘制前执行：

```c
bool full_sized = draw_buf->size == hor_res * ver_res;
if(single_buffer || (double_buffer && full_sized)) {
    /* Wait for flushing before rendering. */
}
```

在 `draw_buf_flush()` 中，只有双缓冲且 `!full_sized` 才在提交下一块之前等待。实际条件见 `src/core/lv_refr.c:708` 与 `:1282`。

判断不包含 `direct_mode/full_refresh`。所以 `size=76800` 像素的两块缓冲，即使设为普通局部刷新，也要先完成上次发送才能开始本次绘制。

| 同为异步驱动、普通局部刷新 | 工程 8.2.0 | 本地 8.3.10 | 本地 9.1.0 |
|---|---|---|---|
| 双缓冲容量小于全屏 | 可先绘制另一缓冲，提交前等待 | 同左 | 同左 |
| 双缓冲容量恰好全屏 | 可先绘制另一缓冲，提交前等待 | **绘制前等待**，限制重叠 | 可先绘制另一缓冲，提交前等待 |
| 整屏失效只有一个大块 | 块内不能边画边发 | 块内不能边画边发，另有上述等待 | 块内不能边画边发 |

因此，9.1.0 的 PARTIAL 双全屏容量路径相对 8.3.10 有更合适的等待位置，但工程 8.2.0 已经具有这种基本时序。不能据此推导升级到 9.1.0 一定优于当前工程。

若未来必须在 8.3.10 使用双全屏容量的普通局部刷新，可做小范围补丁：仅对 `direct_mode=0 && full_refresh=0` 恢复“单缓冲绘制前等、双缓冲提交前等”的策略；其他模式保留原语义。必须同时调整两个等待分支，不能只删掉绘制前等待，否则可能在上一传输尚未完成时再次提交并覆盖 flush 状态。

优先选择小于全屏的实际缓冲容量，可直接避开该分支。不要通过虚报缓冲容量大于已分配内存来绕过判断。

### 2.3 DIRECT 文档与实际调用路径有差异

本地 `docs/porting/display.md:56` 仍写 DIRECT 每轮只 flush 一次、并需用户手动同步；源码却已含自动同步，且 `refr_area_part()` 末尾每个区域都会执行 `draw_buf_flush()`。

v8.3.10 `src/core/lv_refr.c:1302` 将 `draw_ctx->buf_area` 传给驱动；DIRECT 中它为整屏。因此不能按旧文档把现有 `LCD_DisplayArea()` 直接接上 DIRECT，否则一个刷新周期可能发送多次全屏。

若 DIRECT 采用最后一个区域才提交整帧的策略，前面的 flush 也必须正确通知完成，最终传输完成后再通知最后一次 ready。驱动手动同步和库自动同步不能同时启用。

### 2.4 已验证的矩形差集边界问题

`src/misc/lv_area.c:196` 使用 `lw > 0 && sh > 0` 判断左侧剩余矩形，但 LVGL 坐标端点是包含关系；单行合法区域会得到 `sh=0`，从而漏掉左侧需要保留的像素。

最小反例：旧更新区域 A=`(0,0)-(9,0)`，本轮重绘 B=`(5,0)-(9,0)`。正确同步区域应包含 `(0,0)-(4,0)`，本地两个版本都漏掉这 5 个像素。

验证脚本：`Tests/LVGL_Buffer_Host/probe_area_diff.py`。它读取指定源码中的原始 `_lv_area_diff()`，原样提取函数，用 GCC 编译后按像素覆盖检查；基础矩形谓词由主机 shim 提供，使用等价的半径零、包含端点语义。测试坐标统一为 32 位且均在 0..9 内，不依赖目标机坐标宽度。

```powershell
python Tests/LVGL_Buffer_Host/probe_area_diff.py 'C:/Users/ZLK/Documents/Cubemx/lvgl-8.3.10/lvgl-8.3.10'
python Tests/LVGL_Buffer_Host/probe_area_diff.py 'C:/Users/ZLK/Documents/Cubemx/lvgl-9.1.0/lvgl-9.1.0'
```

两个版本结果相同：单行反例漏 5 像素；4x4 网格全部 10000 对合法矩形中，400 对存在差集漏覆盖，3375 对复制了本轮本会重绘的像素。后者是冗余工作，不等同于画面错误；前者可能使待绘制缓冲保留旧像素。脚本因发现漏覆盖返回 1，这是研究结果，不是编译失败。

这是函数级正确性验证，不是整套 LVGL 仿真或真机花屏复现。PARTIAL 路径不调用该同步算法，当前固件不受这条 DIRECT 路径影响。若启用 DIRECT，需修正包含端点的完整差集算法、加入无交集/包含/单行/单列/多重相减测试，再验证缓冲图像。

另外，`:338` 和 `:558` 的同步链表插入结果未经空指针检查即解引用；本机需增加分配失败退化路径或有界区域容器。失败时不能静默丢弃需要同步的数据。

## 3. 工程自身更应优先处理的开销

### 3.1 主菜单每次焦点变化都强制整屏失效

`GUI/GUI_Main.c:282` 的 `GUI_MenuFocusSet()` 在移动焦点、滚动到目标后调用 `lv_obj_invalidate(lv_scr_act())`。方向键经 `GUI_MenuFocusMove()` 进入该路径。

当前库的 `lv_group_focus_obj()` 已对旧焦点和新焦点对象分别 invalidate；因此应优先验证移除这里的整屏 invalidate，保留局部焦点及实际滚动产生的失效。进入页面的首次刷新、主题变化和视频/游戏结束后的整屏恢复不能一概删除。

默认 240 MHz 档，SPI1 为 60 MHz，153600 B 整屏数据仅线速发送就需 20.48 ms。让一次焦点移动只更新必要控件，既减少绘制，也减少发送字节数，收益不依赖更换 LVGL 版本。

### 3.2 同步 flush 阻断绘制/发送重叠

`lv_port_disp_template.c:141` 调用 `LCD_DisplayArea()`；后者在 `Drivers/LCD/LCD.c:382` 忙等 DMA 结束。

现有 `LCD_StreamBegin/WriteAsync/Wait/End` 和 DMA 完成信号量可作为实现参考，但直接在 flush 内调用会等待的 `StreamEnd()`，仍会使 flush 同步化。需要明确的异步事务完成接口。

### 3.3 外部字形读取与移动阴影

实际 Keil 工程编入 `GUI/GUI_Font.c`，未列入根目录模板 `myFont.c`。字体优化和升级检查应针对实际编入文件。

`GUI_Font_GetGlyphDsc()` 读取字形索引和描述；`GUI_Font_GetGlyphBitmap()` 再次读取索引、描述，随后读取位图。代码有单块位图缓冲，但没有按字形键保留并复用内容的缓存。小条带可能增加重复字形查询，应在测试中记录 SPI2 字形读取次数/耗时，避免只看 SPI1 指标。

`GUI/GUI_Message.c:356` 的移动 Toast 有 24 像素阴影，弹窗 `:548` 也有 24 像素阴影；`LV_SHADOW_CACHE_SIZE=0`。常规按钮已普遍关闭阴影，不应将所有页面都归因于阴影。

可测量阴影关闭/减小的收益；需保留视觉效果时，测试 48 的阴影缓存配置。但该版本缓存是软件绘制文件内的静态数组，48x48=2304 B 会进入普通静态 SRAM，而不是自动走 SRAMEX。必须检查 48 KiB `RW_IRAM1` 余量，不能无成本地开启。

## 4. 分阶段实施

| 阶段 | 改动 | 验收条件 |
|---|---|---|
| P0 基线 | 聚合记录渲染、DMA、等待、发送字节数及内存 | 能区分绘制慢、发送慢、无效重绘；不在每次 flush 中打印 |
| P1 局部重绘 | 优先处理主菜单焦点移动整屏 invalidate | 非滚动焦点移动不再固定发送整屏；焦点、背景、遮罩无残留 |
| P2 异步双条带 | 8.2.0，SRAMEX 双 48 行，完整完成通知及显示移交 | 观察到另一缓冲绘制与 DMA 重叠；错误路径和媒体切换无死锁 |
| P3 参数选型 | 比较 24/48/96/120 行与全屏容量 | 用真实页面 P95 完成时间、RAM、CPU 占用选择；不只看峰值 FPS |
| P4 版本对照 | 同一驱动/缓冲/刷新周期下升级 8.3.10 | 页面、字体、图片、焦点及音频回归通过；map 与栈余量可接受 |
| P5 热点优化 | 按剖析结果处理字体缓存、阴影、memcpy 和节拍 | 变化带来可重复收益，不导致音频欠载或内存压力恶化 |

每阶段单独保留可回退配置，避免同时改版本、缓冲、时钟和主题后无法归因。

### 4.1 缓冲配置

推荐先保持 RGB565、`LV_COLOR_16_SWAP=1`、`full_refresh=0`、`direct_mode=0`、刷新周期 30 ms。v8 draw buffer 大小参数是像素数。

| 每块容量，按 320 像素宽折算 | 每块字节数 | 两块合计 | 全屏失效时块数 | 每块最大 DMA 段数 |
|---:|---:|---:|---:|---:|
| 24 行 | 15360 | 30 KiB | 10 | 1 |
| 48 行 | 30720 | 60 KiB | 5 | 1 |
| 96 行 | 61440 | 120 KiB | 3，末块不足 96 行 | 1 |
| 120 行 | 76800 | 150 KiB | 2 | 2 |
| 240 行 | 153600 | 300 KiB | 1 | 3 |

段数按当前 8-bit SPI DMA、65535 字节上限计算。矩形宽度小于 320 时可容纳更多行，真正上限是像素容量，不应在驱动里假定每块永远是固定高度。

首轮可把现有 150 KiB 帧缓冲中的两个不重叠、对齐子区域作为双 48/96 行缓冲，保持分配和资源表接口不变；此时系统仍占用 150 KiB，不能宣称已节省内存。不要分别释放子区域指针。

静态全工程检索显示，当前 `frame_buffer_table` 的像素指针直接使用者为 LVGL 显示移植层，创建入口在 `firmware_start.c`。确认运行时没有额外约定后，再用独立 LVGL 缓冲分配接口替代固定全屏分配，才能实际把 150 KiB 降到 60 KiB。不要直接更改通用 `creat_frame_buffer()` 的全屏容量契约。

不占用 CCM DMA 缓冲，不把常驻 LVGL 缓冲挤入 Video_Memory。SPI 双缓冲也不能保证消除无 TE 信号下的屏幕撕裂。

### 4.2 异步事务与所有权

建议一个静态事务描述符，维护驱动指针、像素地址、剩余字节、事务序号、busy/error 状态；使用现有 CMSIS-RTOS V2 静态信号量。无需第一步就增加显示 feeder 线程。

1. flush 设置窗口和片选，登记事务，再启动首段 DMA 并返回。全屏/半屏较大块需要续传，小条带无需续传。
2. 完成回调核对 SPI1 和所有者，续传后续段；最后一段确认线端传输结束，释放片选，清事务状态，调用一次 `lv_disp_flush_ready()`，并唤醒等待者。ISR 只做完成处理，不创建控件或修改页面。
3. `wait_cb` 等待完成信号并复查事务谓词。不能依赖 handler 返回之后的主循环再调用 ready：LVGL 可能正在 handler 内等待，届时会形成死锁，见 [#4044 的维护者说明](https://github.com/lvgl/lvgl/issues/4044#issuecomment-1465987935)。
4. DMA 启动失败/超时走统一收尾；只有确认 DMA 停止读取源缓冲后才能释放给 LVGL。错误中止、迟到回调和重复通知必须防护；在 LVGL 线程安排后续重绘。
5. 在 `lvgl_ui_pause_point()` 发出 PAUSED 确认之前排空整笔事务。一次 HAL READY 不等于所有分段已发送完。暂停等待期间仍允许完成中断执行。
6. 继续保留 NES/视频原有 DMA 通知，不重新定义第二个全局 HAL 回调。恢复 GUI 时仍请求完整重绘，以覆盖媒体阶段留下的屏幕内容。

现有 SPI1 DMA 配置已经在 USER CODE 中改为 VERY_HIGH、FIFO FULL；不能只看 CubeMX 前面的 MEDIUM/DISABLE 初值后再“优化”一次。IRQ 优先级仍为 6，SDIO DMA 为 5；不在本轮盲目提升中断优先级或更改总线突发。

### 4.3 v8.3.10 升级范围

对当前 Keil XML 的只读检查找到 165 个 LVGL `src` 下 C 文件，全部在 8.3.10 中仍有对应路径；但新版本新增文件不会自动加入 Keil 工程。通用软件绘制至少要核对：

```text
src/draw/lv_draw_layer.c
src/draw/lv_draw_transform.c
src/draw/sw/lv_draw_sw_layer.c
src/draw/sw/lv_draw_sw_transform.c
```

保留并逐项迁移当前 `lv_conf.h` 的自定义堆、RTOS tick、RGB565 swap、字体和裁剪功能；不能直接覆盖成上游模板默认配置。8.3.10 保留 v8 的显示/字体/图片主要 API，迁移成本低于 v9，但结构体和样式系统仍有变化，必须完整重编译。

新版本引入图层机制及 `opa_layered`，按 `src/core/lv_obj_style.c:879`，transform、非满 `opa_layered`、非 NORMAL 混合模式可能触发额外图层。普通 `bg_opa` 不应被一概当成分配整层。模板默认简单图层目标为 24 KiB、fallback 为 3 KiB；这是按需分配目标，不是启动固定占用，也不构成所有 transform 图层的硬上限。

本地 8.3.10 `lv_group_add_obj()` 已先从旧组移除对象，当前工程在弹窗调用处已有显式移除的规避；升级时保留正确行为并回归焦点切换，不因版本变化随手删除应用侧保护。

通过版本对照再决定是否合入。仅采用条带普通刷新时，无需为了性能开启 DIRECT，也无需先给同步算法增加新的内存负担。

### 4.4 后续热点与调度

- 字体先做描述符/索引缓存，再根据命中率考虑有界位图缓存。键含字体身份/代次和 Unicode；安装、卸载、切换后失效；不能缓存当前共享 bitmap 临时指针。大缓存用 SRAMEX，容量先小规模试验。
- 文字/进度条仅在显示值实际变化时更新。播放器已有 `GUI_Player_SetLabelTextIfChanged()`，应复用思路，避免重复改造已优化路径。
- 保持 `LV_DRAW_COMPLEX=1` 以满足现有圆角/阴影；已有日志及重型断言关闭，不建议用关闭 NULL/分配断言换取微小收益。
- `LV_MEMCPY_MEMSET_STD` 从 0 改 1 只作为 ARMCLANG/MicroLIB 实测项，不能假定标准库一定快；分别测对齐和非对齐的片内/外部 SRAM 数据。
- 当前 OS tick 是 1 ms，LVGL 时间取 `osKernelGetTickCount()`；`osDelay(6)` 仅是 handler 调度间隔。先保持刷新/输入各 30 ms，驱动与绘制达标后再比较输入 10~15 ms、刷新 20/30 ms，以及按 handler 返回值有上限地等待。阻塞期间必须能响应显示暂停请求。
- 60 MHz SPI 的整屏发送下限是 20.48 ms，单靠改成 16 ms 刷新定时器无法实现持续整屏 60 FPS。局部更新可更快，但需分别报告。
- 暂不改 FSMC 时序、SPI 数据宽度、CPU 档位或添加 DMA2D 路径；这些是另一组实验，F407 本身没有 DMA2D。先消除已经确认的软件多余工作。

## 5. 验证与决策标准

固定时钟、页面内容、字体、主题和刷新周期。测试无滚动焦点切换、跨行滚动、中文文件列表、Toast、140 ms 页面切换、音乐播放同时操作 UI、反复进入/退出视频和游戏。

实验矩阵：A 当前基线；B 仅缩小焦点失效；C B + 8.2 异步双 48 行；D C 的 24/96/120 行变体；E 与胜出配置完全相同的 8.3.10；F 可选普通模式全屏双缓冲，用于验证 8.3.10 等待分支及局部补丁。每组按固定操作序列重复至少三轮。

记录每轮有效重绘像素、SPI 字节数、flush 次数、渲染 CPU 周期、DMA 起止与等待、最后一段完成时间、输入到可见更新的延迟、P50/P95/最大值。顺带记录字体 Flash 读次数、分配失败、SRAMEX 峰值与最大连续块、LVGL 栈余量、音频欠载/碰撞。

`monitor_cb` 在异步场景可能不包含最后一次发送，内置 FPS 也不等同于面板最终完成频率。GPIO/逻辑分析仪或 DWT 聚合统计应能展示真实的 render/DMA 重叠，不在热路径大量打印日志。

通过标准：画面及色序正确，无同步遗漏、越界、重复 ready 或卡死；媒体切换前事务确已排空；P95 延迟有可重复改善，最大延迟和音频质量不退化；Flash/RW_IRAM1/CCM/SRAMEX 均留有余量。硬件吞吐尚未测得，本方案不承诺倍数或固定 FPS。
